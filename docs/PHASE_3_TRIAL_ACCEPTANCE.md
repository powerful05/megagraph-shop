## 商家实际录入

登录工作台→选择商家→选择JPEG/PNG/WebP主图（不超过10MB）→“生成AI草稿”→人工核对标题、末级类目、SKU编码/规格名称、人民币价格和可售库存→“添加商品资料”→按商品选择“服饰”或“通用实物”→保存草稿→商家核对并“确认当前版本”→发布。当前草稿生成器仍是本地Mock，依据文件名生成占位标题，不是DeepSeek看图识别；消费者导购才使用真实模型。默认草稿类目和规格必须人工更正。

服饰填写颜色、成分、版型、季节、用途及每个SKU对应成衣胸围/衣长，肩宽/袖长可缺失；通用实物每个SKU至少提供一条规格（例如纸张大小、页数、装订、封口），不能拿人体尺码字段代替物品规格。测量方法/误差、图片来源须如实填写；未测性能不填成已确认事实。

更新流程：下架→保存修改→旧确认失效→重新确认→发布。消费者历史卡片仍保留原展示，但当前详情、比较、加购、结算必须重新读取当前资格/价格/库存。订单保存下单时资料快照，不随后来商品改版改变。

实际新建的`#66 本地测试 · 录入验证纸本（未发布）`证明上传、改纸本类目、通用实物资料和SKU保存可操作。该草稿只有测试设定/生成图，保持UNPUBLISHED，不能作为真实商家确认或混进固定65件目录。

## 后续正式试用资料（不阻塞本轮Demo）

为了验证多品类、比较和跨商家供给，建议先提供两家商家的三件实物：一件服饰、两件可比较的通用实物，分属两家商家。这是最小试用批次建议，不凭空增加业务验收数量门槛。图片应为实拍或商家已明确确认来源与实物一致的图片；缺失项可以标“未提供”，不能由模型补造。

每件可按下面模板提交资料，不需要API密钥、个人地址或账号密码：

```text
商家名称：
商品标题与末级类目：
主图文件及来源说明：
SKU编码 / 规格名称 / CNY价格 / 可售数量：
资料类型：APPAREL 或 GENERAL_PHYSICAL
颜色 / 材质成分 / 适用场景：
每个SKU的成衣测量或物品规格：
测量方法、误差及未验证项：
商家是否已核对这份资料及图片：待确认 / 已确认（日期）
```

提供资料后先核对并留作待商家确认的草稿；真实资料不能因为开发者点按钮就被算成商家已核实。当前预览仍H2，不能把录入H2写成真实业务MySQL验收；正式真实供给试用前须另核对数据库运行入口。真实商品不加入测试购物/支付流程来冒充成交，不自动发货。

## 负责人集中检查

1. 点新对话，首先为空白Agent与底部输入框。输入“最近很累，想给自己买点东西”，应必要追问，不从库存猜服饰需求。
2. 补充“开会要手写，找30元以内A5横线纸本”，应取得29元测试纸本和可核验依据。问钢笔防洇墨，不应拿图片、材料或旧助手介绍当性能证明。
3. 新对话找“两款400元以内A5纸本”。选择比较，查看现时资料/价格/库存；进入详情、选SKU和加购，再选另一家商品。历史与当前资料版本不同应明确提示。
4. 购物袋按两家分组，使用测试收件人与“本地Mock地址，不发货”。提交后生成独立子订单；一家模拟成功、另一家失败，应分别CONFIRMED/RELEASED。已有下单组#2可直接核查，无需重复创建订单。
5. 刷新并切换账号历史，消息各一次；另一账号不能看到原列表。发送时停止等待后切换或刷新，说明仅停止浏览器等待，迟到回复留在原会话。失败重试不重复用户消息。
6. 工作台修改一件测试商品的资料或价格并重新确认发布，再打开旧推荐比较；下架后不可加购。购物袋数量大于当前库存，结算应失败且不新增订单。
7. 缩窄到390像素，检查比较、详情、购物袋/订单与对话历史；开启“减少动态”，键盘焦点仍可到达控件，Escape返回。问线上课程、软件授权、预约服务，应讨论目标和未开放能力，不用实物替代。
