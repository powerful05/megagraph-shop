# 阶段 2B：订单履约纵切片

## 目标

在不接入外部物流平台的前提下，让已支付订单继续走到完成：

```text
支付成功 → 商家填写承运商和物流单号 → 订单发货
→ 顾客查看物流事实 → 确认收货 → 订单完成
```

## 默认决策

- 履约状态与支付、库存预占状态分开，使用独立 `shipment` 事实表。
- 本阶段一张订单只允许一张物流单；拆单发货留到后续阶段。
- 只有 `PAID` 订单可以发货，发货后订单为 `SHIPPED`。
- 只有订单所属顾客可以确认收货，完成后订单为 `COMPLETED`、物流为 `DELIVERED`。
- 商家发货使用 `Idempotency-Key`，同一请求重试不会创建重复物流单。
- 承运商和物流单号是商家确认的事实，不由 AI 生成。
- 发货和完成状态变化与 Outbox 事件在同一事务提交。

## API

- `POST /api/merchant/v1/orders/{orderId}/ship`：已支付订单发货，需要 `Idempotency-Key`。
- `POST /api/shop/v1/orders/{orderId}/confirm-receipt`：当前顾客确认收货。
- 原有顾客和商家订单查询响应增加 `shipment` 快照。

## 验收场景

1. 待支付、支付失败、已取消或已超时订单不能发货。
2. 商家只能给自己的已支付订单发货。
3. 重复提交同一发货幂等键只返回原物流单。
4. 发货后商家端和顾客端看到相同的承运商、物流单号和发货时间。
5. 非订单所属顾客不能查看或确认收货。
6. 顾客确认收货后订单为 `COMPLETED`、物流为 `DELIVERED`。
7. 重复确认收货不会重复写入状态或 Outbox 事件。
8. `ORDER_SHIPPED` 和 `ORDER_COMPLETED` 事件与订单状态同事务提交。

## 暂不包含

- 对接顺丰、菜鸟或其他物流查询 API。
- 拆单、多包裹、部分发货和物流轨迹订阅。
- 退货、退款、换货和售后工单。
- 自动确认收货和商家结算。
