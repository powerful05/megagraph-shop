## 真实模型固定问题

问题源为 `apps/backend/src/test/resources/guide-evaluation.json`，运行 `node apps/backend/scripts/guide-evaluate.mjs`。脚本只允许本机 HTTP 测试服务，要求显式启用真实模型、公开目录恰为三件 `LOCAL_TEST` 样本；获取 Session/CSRF 后调用既有对话接口，不读取或传递模型密钥。结果写入被忽略的 `apps/backend/var/`，不写入用户真实对话。

初次 20 题有 1 项失败：仅按标题匹配“上衣”漏掉纯棉衬衫/开衫。引入已有可见类目路径后 20 项通过。人工阅读又发现模糊心情被先导向服饰，增加用途澄清和无商品断言；同时补齐展示顺序上下文，检查“第二件”的指代。

随后完整运行 21 题全部通过。增加未执行订单/支付边界后运行 22 题全部通过，但人工阅读仍发现指代回复与选品结果矛盾、虚构美元分区，补齐断言和提示。再次完整运行 22 题全部通过：有效回复、测试来源、无演示回退、限定 SKU、无供给不出商品、需要匹配时不能漏召回、必要追问、用途不能被服饰限定、跨轮指定商品顺序及不声称已执行交易。单题流程耗时中位数 2145.5 ms，最长 4357 ms（包含该题的多轮调用）；这不是线上延迟承诺。完整本地结果为 `apps/backend/var/guide-evaluation-final.json`。

人工检查确认：预算 180 只选米白针织；纯棉不混入棉粘纤款；颜色和预算改口应用最新约束；没有 XL、手机、真丝、美元标价、课程或服务时不冒充对应供给；尺码讨论说明成衣与人体尺寸不能直接等同。风格与搭配判断仍是模型建议，未由独立用户评分。自动断言通过不等于推荐质量 100%。

人工阅读还看到假设性美元筛选建议、内部展示顺序 JSON 被原样输出；继续收紧回复规则与这两题的断言。首次专项断言误把正常的“上轮展示顺序里的第二件”也判为内部数据，改为检查内部标识标签与 JSON ID，最终两题 2/2 通过，人工确认指代与内容正确。专项结果为 `apps/backend/var/guide-evaluation-wording-final.json`；最后的回复提示改动另通过 11 项模型解析和对话接口测试。测试与启动曾同时编译共享 target 导致一次测试编译失败，串行重新运行通过，不是业务测试失败。导购仍没有写业务事实的工具，直接加购由用户在详情选规格并点击，订单创建和 Mock 支付也由用户明确操作。

## 浏览器闭环

匿名顾客描述“咖啡馆见客户、不要蓝色、单件250以内”，得到米白针织和灰色开衫。打开推荐详情选规格、加购后进入登录，登录后继续同一个 SKU，不偷偷替换规格；再从同一对话加入另一家商品，进入结算生成下单组 #2 的两家试用子订单。A Mock 支付失败、库存 `RELEASED`；B Mock 支付成功、库存 `CONFIRMED`，互不回滚，界面显示模拟成功但不发货。

桌面 1280×900、手机 390×844 检查详情：照片正常加载、无页面横向溢出、移动详情宽度350、规格与加购按钮可见可操作；键盘首尾焦点循环、Escape 关闭后焦点回到打开它的商品卡片。普通通知 6 秒后关闭，错误提示不自动消失。

## 已知限制

真实目录当前只有三件明确标注的测试服饰。大于 50 件与缺失属性场景由自动化样本验证，不声称大目录真实性能已验收；目录仍是现有 JPA 公开读取的内存筛选基线，未来需按规模评测分页/查询优化。真实商家资料、真实用户反馈和更广问题集仍需补充。

一轮最多两次模型调用，日志记录阶段、请求标识、模型、耗时与 prompt/completion token，不记录输入内容。没有模型价格表或费用限额平台，不声称提供精确费用账单。预览服务继续使用本地 H2；MySQL 数据库专项与页面预览是不同环境。无真实收款、虚拟权益交付、服务预约或自动下单；未合入 main 或推送。
