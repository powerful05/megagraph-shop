# 3B 当前约束与空推荐一致性

2026-10-02：处理上一轮预算改口的实际漏选和错误范围说明。继续使用五件明确标注的测试供给、真实 DeepSeek 和本地 H2 预览。没有数据库迁移、库存或订单写入，也未开放数字权益、预约或真实支付。

## 实现范围

内部 `GuideModel.chat` 同时接收对话历史、当前候选和本轮 `GuideIntent`。回复输入中的 `currentIntent` 包含服务端已经采用的预算、币种、颜色、材质、尺码、类别与指代约束；历史助手内容只作对话背景，不再作为当前筛选范围的事实来源。意图本身仍由模型提取，不能视为用户输入的完美解析。

专项逐条阅读仍发现历史介绍污染：预算收紧后卡片只有一款，但建议说“这三款都落在收紧后的范围内”。因此进一步拆开两种历史用途：意图提取继续读取完整用户/助手历史及结构化展示顺序；回复生成保留用户消息，但历史助手消息替换为固定占位说明，不再携带旧介绍、旧候选数量或旧展示 ID。指代定位已由服务端完成，当前候选与当前意图仍明确传入。浏览器保存的会话和传给意图提取的上下文没有删除。

回复 JSON 新增内部 `matchStatus`，公开对话 API 不新增字段，前端共享契约不变：

- `MATCHED`：必须有商品选择，且当前意图无需先澄清。
- `NO_CANDIDATES`：必须为空选择、当前候选确为空且无需先澄清。
- `NEEDS_CLARIFICATION`：必须为空选择，且与本轮意图的澄清标记一致。
- `PURPOSE_MISMATCH`：候选存在，但模型未选出用途合适的商品。
- `REQUIRED_EVIDENCE_MISSING`：候选存在，但模型判断必要性能缺少依据，因此不推荐。

解析器拒绝缺失或未知状态，以及状态与非空/空选择矛盾的 JSON。服务端核对候选数量和澄清标记，防止有合格候选却以 `NO_CANDIDATES` 宣称没有候选。状态矛盾与原有格式/引用错误共用最多一次回复重新生成，不叠加新的重试次数；第二次仍矛盾则撤回回复与卡片。上游错误、意图失败及现时资料变化的处理保持不变。

重新生成仍由模型选择当前候选，不用服务端猜测商品填满结果。用途不合适和未验证性能仍可拒绝推荐。候选存在但空选择时，不显示模型自由文本建议，改用服务端说明：未选出用途合适的推荐，或未返回具备必要性能依据的推荐。这避免把“必须增加预算”等未核对解释继续传给用户，但不能证明模型的用途/性能分类本身完全正确。

非空推荐的结构化资料仍按当前商品版本与 SKU 核对；其 `advice` 仍是自由文本，可能复述资料或作欠准确概括，本轮没有实现通用语义事实检查器。

人工阅读随后发现，收起空推荐建议可能同时收起“不能持续监控”的有效能力回复，而旧“不能/无法/没有”词表误把泛泛的无推荐说明算作通过。因此内部意图新增必填布尔 `requestsMonitoring`，只针对最后一条用户消息的持续监控、主动通知或后续提醒请求；普通现时库存查询及已取消的旧请求不沿用该标记。命中时服务端直接说明不能持续监控、不能主动通知且没有创建提醒，不再查询候选或调用回复模型。公开 API 仍不新增字段。该标记仍依赖意图模型正确理解语言，不能宣称覆盖所有表达。
