# 阶段 2E 契约：身份、MySQL 与统一对话入口基础

状态：**契约已冻结，尚未开始实现**。上位基线为 [SYSTEM_ARCHITECTURE.md](SYSTEM_ARCHITECTURE.md) 第 8、13、20–21 节；阶段 2D 的支付与退款边界继续由 [PHASE_2D.md](PHASE_2D.md) 约束。本文只冻结 2E 的范围、跨端契约和退出条件，不表示真实用户试用已经可以开放。

## 结论与影响

2E 把现有本地演示的 Basic Auth、默认 H2 和分散的商品页，推进为可承接后续试用的正式会话、MySQL 运行基线及统一 AI 超市入口骨架。顾客面对的是**一个跨商家的对话入口**，不是每个商家各有一个消费者商城。2E 只提供入口与视觉基础；跨商家购物车/拆单属于 3A，真实 AI 对话导购属于 3B，动态体验与适量 3D 属于 3C。

当前 `CurrentMerchant` 取第一条商家成员关系；用户一旦属于多个商家，这种隐式选择可能操作错误商家。2E 必须改为显式选择并逐请求校验成员关系。当前前端把 Basic 凭据交给每次 `fetch`，也不能作为真实用户浏览器的身份方案。H2 通过或 MySQL 迁移成功，都不能单独证明会话、租户和浏览器边界可用。

## 目标与非目标

目标：

1. 顾客和商家以同一套服务端会话登录、退出、恢复身份；受控邀请注册顾客账号，避免把本地固定账号带入试用环境。
2. 商家 API 从认证用户与明确选择的商家成员关系推导 `MerchantActor`；公开商品可跨商家读取，私有资源和订单仍隔离。
3. 在独立 MySQL 8.4 schema 上证明全量迁移、已有数据升级、身份与既有交易的持久性；H2 保留为快速测试手段。
4. 顾客端建立可访问、响应式的统一对话入口和设计 Token；保留现有公开商品发现与订单能力，不伪造 AI 回复。

非目标：开放注册、邮箱/短信验证、找回密码、OAuth/第三方登录、平台运营后台、会员/营销、商家自助入驻；跨商家购物车和下单、真实推荐、商家 AI 上架、3D 场景；真实收款、分账、结算和真实履约。2E 不接入任何真实支付、AI 或对象存储凭据。

## 已冻结的默认决策

| 事项 | 2E 决定 | 原因与后续边界 |
| --- | --- | --- |
| 顾客注册 | 邀请码一次性注册；不开放无邀请的公网自助注册 | 首批是受控试用。邀请发放与商家开通由受控离线流程完成，不在 2E 建运营后台。公开注册与验证在扩大试用前另行决策。 |
| 浏览器认证 | 服务端 Session，初期存 MySQL；浏览器只持有 HttpOnly Cookie | 不把 Basic 凭据、Bearer Token 或密码保存在前端状态/持久存储。 |
| API 部署 | 两个前端各通过同源 `/api` 代理访问后端；开发代理与部署反向代理遵循同一约定 | 不依赖带凭据的跨域浏览器请求；不以开放 CORS 代替同源部署。 |
| 商家选择 | 每个 `/api/merchant/v1/**` 请求显式携带 `X-Merchant-Id`，服务端检查该用户对此商家的有效成员关系与角色 | 该头只是选择器，不是授权事实；不得继续使用“第一条成员关系”。 |
| 数据库 | 非测试/演示的 2E 运行使用 MySQL；不启用固定开发账号种子 | H2 仅用于本地离线开发和自动化测试。 |
| 页面入口 | 首屏能看到统一对话输入外观、示例需求、商品示例和清楚的阶段提示 | 输入骨架不得提交假 AI 结果；真实对话请求到 3B 才接通。 |

以上是阶段实现默认值，不是对未来所有经营模式的承诺。若实现证据要求变更路径、字段、数据表、注册边界或会话方案，Worker 先在 `API_OR_SCHEMA_CHANGES` 写出影响，由 Lead 修改本文并审批，再改变跨端实现。

## 身份和 HTTP 契约

### Session 与 CSRF

- 使用 Spring Security 服务端 Session；引入 MySQL 持久化 Session 存储，Session ID 在登录时轮换，退出时服务端失效。建议空闲过期 8 小时；过期、退出和账户禁用后，旧 Cookie 不得再获得私有数据。
- Cookie 使用 `HttpOnly`、`SameSite=Lax`、host-only 和 `Path=/`；非本地 HTTPS 环境必须设置 `Secure`。响应中的身份、CSRF Token、邀请信息和私有数据均为 `Cache-Control: no-store`。
- 所有浏览器写请求，包括登录、注册、退出、商家图片上传和既有订单动作，都要携带 `X-CSRF-TOKEN`。`GET /api/auth/v1/csrf` 可匿名获取 `{ "headerName": "X-CSRF-TOKEN", "token": "..." }`；前端只在内存保留 Token，失效后重新获取。
- 登录导致 Session 轮换后，前端重新读取 CSRF Token；首次请求 403 时只刷新 Token，不自动重放下单、退款等非幂等写操作。
- 2D 的 `POST /api/payment-callbacks/{provider}` 只豁免浏览器会话和 CSRF，仍须按 2D 契约验签。不得将整个 `/api`、Mock 控制入口或登录/注册排除在 CSRF 之外。
- 非测试运行不接受 HTTP Basic 作为浏览器身份。`local/test` 可以为旧集成测试保留受限测试替身，但两个前端必须全程使用 Session 契约。
- 同源代理下不发送跨域凭据；如未来确需不同源部署，必须另行冻结 Cookie 域、可信 Origin 和 CORS，不在 2E 隐式放宽。

### API 路径和响应

| 方法与路径 | 请求 | 成功响应 | 规则 |
| --- | --- | --- | --- |
| `GET /api/auth/v1/csrf` | 无 | `200 {headerName, token}` | 匿名可用；不暴露 Session ID。 |
| `POST /api/auth/v1/register` | `{inviteCode, username, displayName, password}` | `201 {userId, displayName}` | 邀请码一次性兑换；`username` 为规范化的小写邮箱形式登录名，但**不视为已验证邮箱**；注册后仍需登录。 |
| `POST /api/auth/v1/login` | `{username, password}` | `200 AuthMe` | 统一错误，不泄露账号是否存在；成功轮换 Session ID。 |
| `GET /api/auth/v1/me` | Session Cookie | `200 AuthMe` | 未登录返回 `401`。 |
| `POST /api/auth/v1/logout` | Session Cookie | `204` | 使当前 Session 失效；前端清理内存状态。 |

`AuthMe` 固定为 `{userId: number, displayName: string, memberships: Array<{merchantId: number, merchantName: string, role: "OWNER" | "EDITOR" | "PUBLISHER" | "VIEWER"}>}`。无商家成员关系的顾客得到空数组；不暴露密码哈希、邀请信息或内部安全字段。共享类型放在 `packages/domain-types/`，两个前端不能各自定义语义不同的身份类型。

认证/授权错误使用现有统一错误体的稳定 `code`：`AUTHENTICATION_REQUIRED`（401）、`INVALID_CREDENTIALS`（401）、`CSRF_TOKEN_INVALID`（403）、`INVITE_INVALID`（400）、`INVITE_USED_OR_EXPIRED`（409）、`USERNAME_ALREADY_EXISTS`（409）、`MERCHANT_CONTEXT_REQUIRED`（400）、`MERCHANT_ACCESS_DENIED`（403）。登录和注册须有有界限流，触发时返回 `429` 和 `Retry-After`；登录错误对存在/不存在的账号保持相同对外语义。日志、异常和前端监控不得记录密码、邀请码、Session Cookie 或 CSRF Token。

### 商家和公开读取边界

- 所有商家 API，包括 `GET /api/merchant/v1/me`，都要求 `X-Merchant-Id`。缺少/非法选择器拒绝；服务端逐请求查询账户状态、商家状态、`merchant_user` 成员关系和当前角色，再形成 `MerchantActor`。角色不按“某用户在任一商家是 OWNER”做全局放权。账户禁用、商家暂停或成员关系撤销在后续请求立即生效。
- 商家工作台从 `AuthMe.memberships` 选择商家；切换商家时取消旧请求并清空商品、订单、草稿、媒体缓存，再按新选择器加载。已有 `MerchantMeResponse` 返回所选商家与角色，而非第一条关系。
- 私有资源按所选 `merchant_id` 过滤；访问其他商家的具体商品草稿、媒体、订单或 AI 任务返回 404，避免通过 ID 探测存在性。顾客订单仍只按当前 `userId` 访问。
- `GET /api/shop/v1/products`、单件详情和公开媒体继续允许匿名，能读取**所有活跃商家**已发布且可公开的商品资料，不要求或接受顾客选择商家；草稿、未公开图片、内部价格/成本和商家订单不可混入。公开读取不是跨商家交易授权。
- 现有订单仍是一单一商家。2E 不改变购物车、一单一商家的结算约束，也不暗示多商家购物车已经可用。3A 另行冻结统一购物车与拆单契约。

## MySQL、迁移与事实边界

- 保留已提交的 `V1`–`V5` 原样，只新增 Flyway 迁移。2E 最小新增持久事实：一次性 `trial_invite`（邀请码**哈希**、过期时间、兑换时间、兑换用户、唯一约束）和 Spring Session JDBC 所需的 Session/属性表与过期索引；具体标准表 DDL 必须与实际依赖版本匹配。邀请码兑换和 `app_user` 创建在同一事务，唯一约束裁决并发兑换与同名注册，不靠先查后写。
- 受控管理命令生成高熵随机邀请码，只显示一次；数据库仅保存哈希，不提供公网发码 API，也不把明文写进代码、日志或文档。商家账号/成员关系由同样受控的离线流程或测试夹具创建，本阶段没有商家自助入驻。
- `app_user.username` 的大小写规范化和唯一语义必须在 H2/MySQL 一致；升级既有数据前先检测大小写碰撞，不能静默合并、删除或覆盖账号。沿用 `app_user`、`merchant`、`merchant_user` 的现有主键和角色，不能重写历史迁移。
- Session 表属于认证状态，不是商品/交易事实；商品、SKU、价格、库存、订单、支付与退款仍以 MySQL 业务表为唯一事实。认证变更若产生 Outbox 事件，事件与业务状态变更同事务提交；Session 创建/续期本身不要求新增业务 Outbox。
- 2E 的正式运行必须显式选择 MySQL，缺少该配置不得悄悄回退到当前默认 `local` H2；`APP_DEV_SEED_ENABLED=false`。不能以 `local,mysql` 加测试账号的组合充当可试用部署。迁移验证同时覆盖空 schema 和带有 `V1`–`V5` 测试数据的升级 schema；不清理已有业务数据来制造成功结果。
- 2D 的 Mock 支付只在 `local/test` 可用。2E 不为真实用户开放支付；3A 必须另行设计受控试用环境中的 Mock 支付启用与试用库存/真实履约隔离，不能简单打开本地 profile 或真实渠道。

## 统一对话入口与视觉契约

- 顾客端是一个 AI 超市入口。首页首屏在桌面和移动端都清楚呈现平台识别、自然语言输入外观、女装基础款穿搭示例问题、公开商品示例、登录/购物入口；不为每个商家生成独立商城首页。
- 2E 的输入框是**明确标注的未开放骨架**：可展示交互状态和示例需求，但提交后不得伪造模型回复、推荐理由或可购买的跨商家搭配。真实对话会话、轮次、追问和商品证据字段在 3A/3B 冻结。
- 建立共享的视觉 Token（色彩、排版、间距、圆角、阴影、动效时长/曲线）与顾客端组件基础（导航、输入框、示例提示、商品卡、加载/空/错误状态）。商家工作台保持一致的基础字体、焦点和状态语义，不要求本阶段重做全部页面。
- 体验方向为克制、细腻、有动态层次的品牌官网；2E 只做轻量过渡和交互反馈，不引入 WebGL/3D 运行时。尊重 `prefers-reduced-motion`，支持键盘、可见焦点、触屏和窄屏；无动画时内容与操作仍可用。
- 首屏公开内容和 SEO 元信息由 Nuxt 服务端可见，私有身份/订单数据不在公开 HTML 中泄露；页面从 Session 恢复身份，401 时回到登录状态。公开商品卡从 MySQL 公共 API 读取，不把静态示例当作真实库存与价格。
- 两端 `fetch` 改走同源 `/api`，统一处理 `401`、`403`、`429`、CSRF 失效和网络错误；不再从输入框收集并长期保存 Basic 密码。下单、支付、退款等既有异步状态继续以服务器查询为准。

## 工作拆分与目录所有权

## 验收矩阵与退出条件

### 后端 H2 集成测试

1. 注册邀请仅可兑换一次；并发兑换和大小写等价用户名只创建一个账户；故意使账号创建失败时邀请兑换回滚；禁用账号不能登录。
2. 匿名获取 CSRF 后可注册/登录；登录轮换 Session ID；退出、过期或账户禁用后私有 API 返回 401；缺失/错误 CSRF 的浏览器写请求被拒绝。
3. 非测试配置下 HTTP Basic 不能绕过 Session；登录失败不枚举账号，限流能返回 429。支付回调仍只通过 2D 验签路径，不因免 CSRF 变成无保护状态写入口。
4. 同一用户属于两个商家时，选择器正确切换且仅能读写当前商家数据；撤销成员关系、降级角色、暂停商家后，旧 Session 的后续请求立即失权；不能通过另一商家的 OWNER 身份越权。
5. 顾客匿名读取两个活跃商家的已发布商品，不能读取草稿、非公开媒体或暂停商家的商品；顾客订单仍按本人隔离，既有单商家支付/退款链路不回退。

### 真实 MySQL 8.4 迁移与运行冒烟

1. 独立空 schema 从 `V1` 执行至 2E 新迁移，Flyway `validate` 通过；另从已有 `V1`–`V5` 数据升级，原商品、订单、Inbox 和 Outbox 行数及关键状态不变。
2. MySQL 唯一约束真实阻止重复邀请兑换和规范化用户名碰撞；Session 写入、重启恢复、过期清理可用。启动和重启都不依赖开发账号种子。
3. 使用受控邀请创建顾客、登录并访问购物车；创建两个商家的成员关系并验证切换隔离；在同一 MySQL schema 验证至少一个既有单商家订单与 2D Mock 异步支付流程仍正常（仅在隔离测试配置内启用 Mock）。
4. 记录所用 profile、schema、迁移版本、测试结果及是否跳过；H2 通过不能替代 MySQL 结果，不能借用含个人业务数据的 schema 做破坏性冒烟。

### 浏览器验收

1. 顾客在新会话访问首页，立即看见统一对话入口、示例需求和跨商家公开商品；输入未开放时得到诚实提示，不产生假 AI 回答。刷新后公开页正常，私有页根据 Session 恢复。
2. 邀请注册、登录、退出、刷新、Session 过期和重新登录完整走通；浏览器请求中没有 Basic `Authorization`，前端持久存储中没有密码/Session ID/CSRF Token。
3. 商家账号属于两个商家时，切换后商品和订单不串店；越权链接/旧页面请求不能显示另一商家的私有内容。顾客能跨商家浏览，但不能由 2E 页面假装完成跨商家下单。
4. 在桌面、约 360px 手机视口、键盘操作和减少动态设置下检查首页、登录和错误/空状态；无 WebGL 或脚本动画时不影响核心信息。两个前端生产构建和类型检查通过，根目录 `pnpm verify` 通过。

只有上述证据完整、无未处理的身份/租户越权或 MySQL 迁移问题，并由 Lead 集成到基线，才可称 **2E 实现完成**。这仍不代表可开放真实用户 AI 购物试用：3A 的真实女装供给、跨商家拆单与隔离 Mock 交易，以及 3B 的真实模型导购和评测仍是后续门槛；5A 的真实收款主体与资金路径依然未解决。
